Two extra heads, one changed byte

I added value-cache stores to a query/key preparation kernel. The normalization formula stayed the same. Yet one query element that stock produced as 0.8125 became 0.875.

The extra work changed the row count used to choose a GPU launch tile. That changed how the compiler grouped floating-point additions. A tiny rounding difference became a different FP8 byte. Fixing the first failing inputs was not enough: a wider sweep found another failure, and the final repair needed a stock fallback.

This was the most useful lesson from my Open Kernel Challenge serving project. I began with expert scheduling, then tried attention-preparation fusion. The best observed aggregate score was 1.0251× against unmodified SGLang. Repaired attention fusion passed official evaluation at 1.0224×, but these separate runs did not establish an incremental performance benefit.1

1.About the work I ran this project with coding and research agents. They investigated source, implemented changes, ran probes and reviewed results; I directed the project and made the final risk decision. The independent reviewer mentioned below was a separate research agent. This article describes that collaboration.

To explain the bug, I need to start with the server and the earlier scheduling work. Both optimizations tried to remove work around existing kernels. Attention fusion also had to preserve rounded values written into persistent cache state.

The server I started with

The reference system—called stock throughout this article—served Muse Spark Open with SGLang v0.5.23 at commit 297e54fd on eight H200 GPUs. It used NVFP4 quantized weights, an FP8 key/value cache, tensor parallelism and expert parallelism across eight ranks, and DFlash speculative decoding with an eight-token block. The official scored run evaluated 1, 4, 16 and 32 concurrent users. 12

2.A rank is one participating process Here there is one per GPU. Tensor parallelism divides tensor operations across ranks; expert parallelism assigns different experts to different ranks. NVFP4, BF16 and FP8 refer to numerical representations, not different model architectures.

First, prefill processes the prompt and builds its key/value cache. During generation, the draft model proposes tokens; the larger target model checks them in a verification step. Accepted tokens advance the conversation, while the cache and other state must remain consistent with the accepted sequence. Inside each target step, attention reads cached history and the mixture-of-experts layers process routed activations. That is the loop I was optimizing. 2

A kernel benchmark measures one operator. Serving also includes scheduling, drafting, communication and cache management. An optimization helps wall time only to the extent that it removes work from the exposed critical path.

For a simple serial model, Amdahl's law gives the limit: if a fraction f of runtime is accelerated by a factor s, the total speedup is: 3

S = 1 / ((1 − f) + f / s)

A component that occupies 5% of a serial runtime and becomes twice as fast gives only 1.0256× overall. This is an illustration; the calculation below applies the same discipline to the attention experiment.3

3.Further readingCMU's LLM Serving slides explain batching and cache management—the work around the model that also contributes to request latency.

Testing locally on a different GPU

Local probes ran on an L40; official serving ran on H200s. The L40 could expose indexing, conversion and replay failures quickly. It could not execute the target H200 attention path or establish the full server’s performance.

Expert parallelism changes the size of the problem

My first focus was the mixture-of-experts path. An expert is a feed-forward subnetwork; Muse routes each token to eight of 256 of them. With eight-way expert parallelism, each rank owns 32 experts. The router produces global expert IDs, so each rank must translate the IDs it owns into local numbering and mark the others inactive.

SGLang already used Marlin, a family of quantized matrix-multiplication kernels, for the experts. The pinned model’s first GEMM produces gate and up projections together: N = 8192 output columns, K = 4096 input components. After activation, the second projects back with N = 4096, K = 4096. Scheduling had to preserve these computations. 4 5

Public kernel-track reports by georgxzh, alygg77 and hariappi suggested a useful starting point: retain Marlin’s NVFP4 computation and investigate the scheduling around it. Their component results supplied a lead; I still had to test that mechanism inside this distributed server. 6

Each routed activation supplies one routed-token row of the expert’s input matrix. Quantized packing changes the weight storage, not this logical geometry:

Start with the route map

A Triton kernel first replaced the GPU’s global-to-local expert-ID mapping, preserving -1 for non-local routes and leaving the CPU path unchanged. It passed at 1.0088×. With mixed chunking—a scheduler option combining prefill and ongoing generation—the same patch scored 1.0149× in a separate run. 5

The next question was occupancy. A Marlin row tile groups routed-token rows for computation; a lightly loaded expert leaves some of its slots unused.

Schedule by expert occupancy

Two forwards with the same token count can distribute their routes very differently. Scheduling by each local expert’s load could avoid giving a 12-route expert the same tile as a 50-route expert.

Smaller tiles are not automatically better: they can change weight reuse, occupancy, launch overhead and numerical accumulation. I wanted to classify whole experts, then preserve the existing computation within each class.4

4.Two different numbers The threshold selects the class. The tile size says how many rows that class processes at a time. In the accepted variant those numbers are 16 and 32, respectively.A row-slot illustration, not a timing estimate.

A smaller tile was not automatically a better tile

The first version used a 16-row tile for lightly loaded experts. Local comparisons failed through the first projection, activation and second projection. Keeping Marlin’s arithmetic source had not preserved its accumulation grouping before BF16 rounding. I excluded that version and tested a 32-row tile separately.5

5.Further readingSi Böhm's CUDA matmul worklog walks through how tiling changes data reuse and execution. CMU's GPU Architecture & CUDA Programming slides cover the thread hierarchy behind those choices.

The version that survived

The accepted schedule used a 32-row tile for experts with at most 16 routes, retaining the stock larger tile for the rest. Its shape-derived eligibility covered 116–512 tokens per forward in this configuration, rather than branching on benchmark user labels.6

6.Why token count? The kernel sees tensor shapes and expert loads. The number of users is only an indirect guide to those shapes, especially during ramp-up, prefill and draining.
How the partition works, and where 116–512 comes from

The stock heuristic stops trying larger tiles when T × 8 / 32 / M < 0.9. At M = 32 this is T / 128 < 0.9; 116 is the first integer token count that proceeds to a larger tile. The adaptive guard also requires T × 8 ≤ 16 × 256, giving T ≤ 512. These are dispatch limits, not universal optimal thresholds.

The partition is:

# Explanation only: real classification runs on the GPU.
local_ids = map_global_to_local(global_ids)  # -1 means non-local
live = local_ids >= 0
bins = where(live, local_ids, num_local_experts)
loads = histogram(bins, num_bins=num_local_experts + 1)
small = live & (loads[bins] <= 16)

small_ids = where(small, local_ids, -1)
large_ids = where((local_ids >= 0) & ~small, local_ids, -1)

# Each live route belongs to exactly one class.
run_marlin_for_class(small_ids, row_tile=32)
run_marlin_for_class(large_ids, row_tile=stock_tile)

The extra histogram bin keeps inactive routes from indexing with -1. They remain masked out regardless of that bin's count. The two execution classes must be disjoint, cover all live routes, and retain the original route weights and finalization semantics.

For example, global IDs [32, 33, 7, 32, 65, 33] become [0, 1, -1, 0, -1, 1]. With full-forward loads of 12 and 50, the small class keeps expert 0 and the large class keeps expert 1. Route weights remain at their original positions.

Both classes pass through the existing projections and activation. Shared temporary storage must not overwrite live outputs, including under CUDA graph replay, which reuses captured GPU operations with new inputs at stable addresses. The tests changed route inputs between replays to catch stale-state bugs.

Fuse the integer work around the experts

The new schedule required mapping, counting, classifying and splitting routes. I combined this bookkeeping into one Triton kernel to reduce launches and intermediate tensors.

The GEMM People report explored similar route/dispatch fusion on a different model and B200 hardware. It suggested looking at the small operations between the GEMMs as another place to save launches. 7

The classifier maps IDs, builds a histogram and writes two masked route arrays. It changes neither activation precision nor route weights.

Because this kernel only performs integer bookkeeping, it does not regroup a floating-point reduction. It still needs correctness tests: every live route must appear once, non-local routes must remain inactive, and indexing, masking and changing-input graph replay must match the reference.

The adaptive parent scored 1.0247×; fused classification scored 1.0251×, a nominal difference of about 0.04%. These separate runs do not establish that fusion improved serving speed. What the implementation demonstrably changed was the number of bookkeeping launches and temporary arrays; the combined patch passed all four loads. 87

7.A name in the run logs “Fused-stock” means this expert patch with stock launch flags. The code is modified; the flags are unchanged.

A second opportunity: work before attention

With a passing expert schedule, I turned to preparation for FlashAttention-3 (FA3). Here the intermediate values were floating-point, and the writes changed persistent cache state.

Attention compares queries Q with keys K to combine values V. The KV cache retains earlier keys and values. Before attention, RMS normalization scales each Q/K head vector and rotary position embeddings (RoPE) encode position. I changed the preparation around FA3, not these underlying methods. 9

Stock performs QK normalization/RoPE, K and V casts, a cache store, and a query cast. SGLang already had related fusion machinery; I adapted it to eligible FA3 calls while preserving the backend’s contracts. 10

Variant A fused the FP8 KV conversion and store while retaining a BF16 query output. The ordinary query cast remained before FA3. Variant B also emitted the FP8 query, making the downstream same-dtype cast a no-op. Both were built on the earlier fused expert patch, using stock launch flags.

Step through stock preparation, then switch to repaired Variant B to see which temporary tensors disappear. The repaired option includes the tile selection and fallback explained below.

Triton’s fused-softmax tutorial gives a small, runnable example of this idea: keep intermediate work in one kernel instead of repeatedly materializing tensors. In this case, however, one of the outputs was the cache that future tokens would read.

Moving the store means taking responsibility for it

Each call must write its assigned cache slots, skip padding slot zero, and preserve every other slot. The next graph replay can use different locations. The illustration follows two calls so that stale locations or accidental overwrites would be visible.

Backend eligibility and producer–consumer ordering

Fusion applied only to compatible FA3 decode/target-verify calls with the expected unscaled FP8 cache. Prefill, mixed batches and other backends retained ordinary preparation. Full-attention/sliding-window location selection and the backend’s cache-ownership wait stayed intact.

Programmatic Dependent Launch (PDL) can start a consumer before its producer fully finishes, so device ordering still matters. Removing the query cast required auditing FA3’s launch chain. The pinned source contained the ordinary launch boundary needed before attention read the fused outputs; L40 tests could not execute the H200 PDL handoff. 10

An eligible fused call owns the cache write; an ineligible call restores the ordinary backend writer. Correct arithmetic is not enough if fallback writes twice—or never writes.

Preserve the rounding boundary

Stock materializes BF16 values before the FP8 conversion. Fusing those operations must not accidentally convert an earlier FP32 intermediate directly to FP8. The intermediate rounding can change the result:

FP8(BF16(x)) can differ from FP8(x)

The conversion preserved BF16 rounding and the pinned PyTorch 2.14.1 behavior: finite overflow and infinity saturate to ±448; NaNs retain their sign. An earlier research note had incorrectly predicted NaN for finite overflow. 118

Team 7013’s report using NKI (Neuron Kernel Interface) had also highlighted BF16 rounding boundaries. That was a useful warning, but preserving conversion still did not prove the preceding normalization was unchanged. 7

8.Fusion is not permission to skip rounding A temporary tensor may disappear; its numerical effect may still be required.

The local conversion tests included production-path byte comparisons and probes using all 65,536 BF16 input encodings. Those checks addressed conversion behavior; they did not exhaust the possible inputs to the normalization that produced those values.9

9.A related systems exampleGPU-accelerated Weight Teleportation looks at intermediate handoffs in RL weight synchronization. It is a separate application of the same question: how much work happens between the expensive operations?

The failure hiding at a tile boundary

A separate research agent reviewing the implementation noticed that adding V changed the row count used to choose the Triton launch configuration. The initial tests had missed the relevant boundaries.

On one rank there are 16 Q heads and two K heads, each a 64-component vector. Stock prepares 18 × T head-vector rows. Adding two V heads makes 20 × T. Triton’s BLOCK_M is the number of these head-vector rows grouped in a launch tile—not Marlin’s earlier routed-token tile.

At T = 56, stock sees 1,008 rows while fusion sees 1,120. They fall on opposite sides of a 1,024-row configuration boundary. At T = 410, the counts are 7,380 and 8,200, straddling another boundary at 8,192 rows.10

10.Two meanings of “row” The earlier Marlin row tile groups routed token activations for an expert. Here, Triton’s BLOCK_M groups head vectors for Q/K preparation. Both are tiling decisions, but they belong to different kernels and count different work.

Targeted tests found query-byte failures in both original candidates. Variant A failed seven eager cases and eleven graph cases; Variant B failed two eager cases, at T = 410 and T = 416. The failures were finite values, independently reproducible—not just a disagreement over NaN representation. A’s T = 56 boundary can occur with seven eight-token verification requests. The larger T = 410 and T = 416 cases tested the kernel beyond the ordinary 32-user, eight-token verify regime; I retained those failures rather than exempting those inputs.

To isolate the cause, the controlled probes held the saved failing inputs fixed and varied the launch tile. Forcing stock to use the fused tile reproduced differences; matching stock’s tile fixed the original minimized failures. Another probe disabled arithmetic contraction, which changes whether eligible multiply/add operations combine into one rounded instruction. That did not remove the across-tile discrepancy.

The generated compiler code showed why the launch could matter. In one tile family, each thread accumulated four square contributions before exchanging partial results with other threads; another accumulated eight. FP32 addition is not associative: regrouping the additions can change the rounded sum.

RMS normalization scales a head-vector component by 1 / sqrt(mean(x²) + epsilon), with a small constant epsilon for numerical stability. A changed sum of squares can move an output across a BF16 midpoint. Subsequent FP8 conversion can expose the difference in the stored byte. Here E4M3 means one sign bit, four exponent bits and three fraction bits.

The normalization formula was unchanged, but its FP32 sum was now grouped differently. NVIDIA’s floating-point guide explains why that matters; the saved inputs made it possible to reproduce the effect in this kernel. 12 13

The first repair was still incomplete

The first change selected the tile using stock's Q+K row count while keeping the grid large enough for Q+K+V:

# Simplified from the repaired FA3 preparation path.
config_rows = tokens * (num_q_heads + num_kv_heads)
block_m, num_warps = triton_config(config_rows)

work_rows = tokens * (num_q_heads + 2 * num_kv_heads)
grid = ceil_div(work_rows, block_m)

That fixed the original fixtures. A wider boundary sweep then found query/key discrepancies in the stock BLOCK_M = 32 family, including T = 3641. Matching the tile alone had failed again.

The final repair kept stock’s Q+K-based tile selection for the supported families and sent the entire BLOCK_M = 32 family through ordinary preparation. Fused launches still covered all Q+K+V rows. I did not resolve the wider-family arithmetic discrepancy, so that case used the stock path.11

11.A family, not a list of exceptions With these head counts, T = 3641 gives 18 × 3641 = 65,538 Q/K rows, entering the stock BLOCK_M = 32 family. Eligibility follows shape and head metadata rather than naming individual failing token counts.

From a repaired kernel to the final submission

The three retained minimized failures were Variant A / T = 52 / no RoPE, Variant B / T = 410 / no RoPE, and Variant B / T = 416 / RoPE. They failed before repair and passed afterward. The repaired path then passed 2,048 comparisons: every T from 1–512, both RoPE modes and two finite seed families, against an independently imported pinned-stock reference. Checks covered query/key/cache bytes, dtypes and stride.

Separate tests covered exceptional values, tile boundaries, changing graph inputs and cache locations, padded rows, untouched slots, and actual model dispatch back to stock. The model tests exercised real preparation and cache writes, but used a stand-in for the attention computation. Six configurations also compiled for SM90, the H200’s GPU architecture target. Compilation still did not execute FA3 or PDL on that hardware.12

12.Inside the sweep 512 token counts × two RoPE modes × two finite seed families. Every count in that interval was tested, with additional suites for exceptional values and graph replay.

On the L40, preparation saved 4.56–5.21 μs per layer at T = 8, 52, 56, 128, 256, 410 and 416, with and without RoPE. This is the range of median savings across those cases, not a confidence interval. The benchmark covered QK/RoPE preparation, casts and cache writes; it excluded CPU dispatch, projections, FA3, communication and the rest of serving.

The H200 check was still queued at final selection. I chose repaired Variant B as the final experiment, preserving the earlier 1.0251× entry. It used the fused expert schedule and unchanged launch flags, with neither the original failed variants nor mixed chunking. 14

Official evaluation passed 176 reference turns, later-turn checks across 45,154 served positions, and memory 0.2 GB/GPU below stock. These are model-agreement checks, not exhaustive byte comparisons. The pass supports integration in that evaluation; it does not establish every branch’s activation or prove every PDL dependency.

The serving results

The score was 1.0224×, below the earlier fused expert schedule’s 1.0251×. The metric compares throughput at stock’s per-user interactivity point for each load and aggregates those ratios geometrically. In other words, it rewards throughput while accounting for the per-user serving rate, rather than reporting a kernel’s maximum raw tokens per second. The final run’s ratio was slightly higher at four users, matched at sixteen to the reported precision, and was lower at one and thirty-two. The aggregate difference is 0.0027, or about 0.263% relative to the earlier score. These were separate official runs with their own stock references, not randomized repeated comparisons between the two candidates.13

13.The stock reference Each candidate was measured against stock in its own run. To isolate a small difference between patches, I would want repeated, alternating measurements on the same hardware and workload.

The raw 32-user measurement had only one repetition, which cannot estimate run-to-run variability. No confidence interval for the difference between these candidates is available.

How much saving could reach the server?

The local timings provide a scale for the hypothesis, not an explanation of the H200 result. If all 62 target attention layers saved the same 4.56–5.21 μs during an eligible forward, the total would be:

62 × (4.56–5.21 μs) = 0.283–0.323 ms

For an illustrative 20 ms generation cycle, that is 1.41–1.62% of cycle time, or about 1.014–1.016× speedup if the entire saving reduces wall time. The 20 ms denominator is an assumption, not a measured H200 step time. Neither is this an upper bound: per-layer savings on H200 could be different.

One target verification pass handles several proposed positions together; multiplying again by the eight-token draft width would count the work twice. If a cycle emits a accepted tokens, both its time and its saving divide by a. Eight ranks running in parallel do not multiply the wall-time saving by eight.

The real budget needs H200 measurements of eligible calls, critical-path preparation time and integration overhead. Prefill and fallback calls retain stock preparation; overlap can hide saved device work. The returned logs lacked invocation counts and a profiler trace. The arithmetic does not establish why the score was lower, or that the gap was noise. It shows what to measure next. Timing cases and reproducible calculation.

Other things I tried or considered

Three other experiments changed what I was willing to submit:

  • Expand NVFP4 weights and use BF16 GEMMs for large prefill. Faster individual GEMMs did not rescue complete-path local performance, and numerical comparisons failed. The larger operation had to pay for its preparation too.
  • Prefix-specialized Marlin scheduling. One run hit a watchdog stall: the server exceeded its progress timeout. A later combined candidate passed, but neither that pass nor local controls identified the original cause. I kept the family out.
  • Shorter DFlash drafting. Reducing the proposed block passed a 16-user check but returned an indicative 0.981× ratio. Less verification work per step did not guarantee more useful output per second.

Other leads—including tokenization caching, padding masking, compilation specialization and a larger attention replacement—are indexed in the project evidence map and research ledger. None is part of the final patch. Fused scheduling with mixed chunking passed individual checks but did not receive an all-load scored run; choosing attention left that comparison unanswered.

For related negative results, see alygg77’s measured kernel experiments. The thethings.ai projection worklog separately examines projection optimizations. The unported attention lead was vjeux’s public implementation; its porting requirements are recorded in the ledger.

What I would carry into the next project

I would get target-hardware feedback earlier. The L40 was valuable for rejecting incorrect code, but I spent the last part of the project qualifying a path whose H200 integration and benefit were still unknown. Earlier paired serving measurements would have made the final choice less speculative.

I would also design boundary tests alongside the first optimization, not after the first review. A dispatch heuristic is part of the executable program. Its thresholds deserve adjacent test cases, retained failure fixtures and changing-input replay just as much as the arithmetic body does.

The best observed aggregate was 1.0251×. Repaired attention fusion passed, but these runs did not establish an incremental performance benefit. The durable lesson was the bug: adding V stores changed the launch geometry of QK normalization and exposed different rounding. Dispatch boundaries belong in the first test plan, alongside arithmetic and cache ownership.
