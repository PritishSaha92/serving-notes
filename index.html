The kernel got faster. Did the server?

The most useful result from my Open Kernel Challenge project was not the highest score. It was a discrepancy: the final attention-preparation path was faster in local measurements, passed the official serving checks, and still did not improve my best recorded serving score.

My best expert-scheduling submission scored 1.0251× against unmodified SGLang. The final submission, which added attention-preparation fusion, scored 1.0224×. Both passed correctness checks. These separate runs are too limited to establish a significant regression, but the extra optimization did not produce a demonstrated end-to-end win.

I entered the serving track to learn how GPU optimization behaves inside a real inference system. The work began with a small change to expert routing, grew into occupancy-aware scheduling, and ended with a repaired attention-preparation path. Following that progression shows what changed between the submissions and what the measurements actually established.1

The question running through these experiments was: what unnecessary work can I remove while preserving the computation that the rest of the server expects? I could reduce launches or change a tile and still get the same mathematical formula. The harder part was preserving the actual numerical and stateful behavior.

1.How this project was built I used coding and research agents for source investigation, implementation, probes and independent reviews. “I” refers to the project I ran; it does not mean I hand-wrote every kernel or personally completed every resource in the reading list.

First, define the system being measured

The reference system—called stock throughout this article—served Muse Spark Open with SGLang v0.5.23 at commit 297e54fd on eight H200 GPUs. It used NVFP4 quantized weights, an FP8 key/value cache, tensor parallelism and expert parallelism across eight ranks, and DFlash speculative decoding with an eight-token block. The official scored run evaluated 1, 4, 16 and 32 concurrent users. 12

2.A rank is one participating process Here there is one per GPU. Tensor parallelism divides tensor operations across ranks; expert parallelism assigns different experts to different ranks. NVFP4, BF16 and FP8 refer to numerical representations, not different model architectures.

First, prefill processes the prompt and builds its key/value cache. During generation, the draft model proposes tokens; the larger target model checks them in a verification step. Accepted tokens advance the conversation, while the cache and other state must remain consistent with the accepted sequence. Inside each target step, attention reads cached history and the mixture-of-experts layers process routed activations. That is the loop I was optimizing. 2

A standalone kernel benchmark answers a narrow question: how long does this operator take on these inputs? A serving benchmark also includes scheduling, draft execution, communication, memory pressure and the sequence of requests. A faster operator may occupy little of the exposed critical path, or its integration may introduce work elsewhere.

For a simple serial model, Amdahl's law gives the limit: if a fraction f of runtime is accelerated by a factor s, the total speedup is: 3

S = 1 / ((1 − f) + f / s)

If a component occupies 5% of the total and becomes twice as fast, this model gives only about 1.026× overall. This is an illustration, not an estimate of my attention path. In a distributed server, overlap makes it especially important to identify exposed time rather than add operator durations together.3

3.Study connectionCMU's LLM Serving slides provide background for batching and cache management. They are useful alongside this system diagram; they are not evidence for the measurements below.

Two machines, two kinds of evidence

I could run local probes on an L40. The official evaluation ran on H200s. This split was useful for finding indexing, conversion and replay failures, but it was a poor substitute for profiling the target server. A local preparation benchmark did not execute the target H200 attention backend or the full eight-rank model.

I kept three categories separate: source reasoning, local experiments, and official serving results. A source audit could justify a test; a local test could reject an idea; an official pass could validate the submitted bundle on that workload. None of those automatically proved a universal speedup.

Expert parallelism changes the size of the problem

My first focus was the mixture-of-experts path. An expert is a feed-forward subnetwork; Muse routes each token to eight of 256 of them. With eight-way expert parallelism, each rank owns 32 experts. The router produces global expert IDs, so each rank must translate the IDs it owns into local numbering and mark the others inactive.

SGLang already used Marlin kernels for the experts’ quantized matrix multiplications, or GEMMs. In the pinned model, hidden_size = moe_hidden_size = 4096. The first multiplication produces the gate and up projections together: N = 8192 output columns, K = 4096 input components. After the activation, the second projects back with N = 4096, K = 4096. Those are the dimensions the scheduling work had to respect. 4 5

Public kernel-track reports by georgxzh, alygg77 and hariappi suggested a useful starting point: retain Marlin’s NVFP4 computation and investigate the scheduling around it. Their component results supplied a lead; I still had to test that mechanism inside this distributed server. 6

To see why the route count matters, write the first expert projection as a matrix multiplication. Each routed activation supplies one row of Aₑ. One output entry is the dot product of that row with a column of the expert’s logical weight matrix. Quantized packing changes how the weights are stored, but it does not change these logical dimensions.

Start with the route map

The first submitted change was deliberately small: a Triton kernel replaced the GPU-side global-to-local expert-ID mapping. It looked up each global ID in the ownership map, wrote the corresponding local ID, and kept non-local routes at -1. The CPU path stayed unchanged. This mapping-only entry passed and scored 1.0088×. The same patch with mixed chunking—a scheduler option that combines prefill and ongoing generation work—later scored 1.0149×. These were useful early baselines, not a reason to assume that every subsequent change would add to the score. 5

Once the routes were local, the next question was how much work each expert actually received. A row tile is the group of activation rows processed together by a matrix-multiplication kernel. A larger tile can improve reuse when it is well occupied, but a lightly loaded expert may leave many of those row slots unused.

Schedule by expert occupancy

The important scheduling quantity was not just the number of tokens in the forward. It was the number of routes assigned to each local expert. Two forwards with the same token count can produce very different expert loads.

Imagine two experts receiving 12 and 50 routes. A row tile sized for the busier expert can waste work on the quieter one. Making every tile smaller is not free either: it can change launch count, weight reuse, occupancy and the kernel's numerical reduction strategy.

The weight dimensions stay fixed while the useful activation rows change. A 12-route expert does not acquire more useful rows merely because the whole forward has hundreds of tokens. That is why I wanted to classify experts individually instead of applying one smaller tile to the entire forward.4

4.Two different numbers The threshold selects the class. The tile size says how many rows that class processes at a time. In the accepted variant those numbers are 16 and 32, respectively.A row-slot illustration, not a timing estimate.

A smaller tile was not automatically a better tile

The first version tried a 16-row tile for lightly loaded experts. It failed a local numerical comparison. Diagnostic runs traced the discrepancy through the first projection, activation and second projection. Changing a tile can change FP32 accumulation grouping before BF16 rounding, even when the nominal data types and model equations stay the same. The original failure was retained; an official check passing did not erase it.

That made “same kernel, different launch” an insufficient correctness argument. The 16-row candidate stayed rejected. The accepted 32-row variant had its own tests and submitted identity; it was not a relabeling of the failed experiment.5

5.Study connectionSi Böhm's CUDA matmul worklog is a good companion for understanding why tiling changes reuse and execution. CMU's GPU Architecture & CUDA Programming slides cover the thread hierarchy and reductions. Neither establishes numerical equivalence for this Marlin path.

The version that survived

The successful adaptive variant used a 32-row tile for experts with at most 16 routes, retaining the stock larger tile for the other experts. The dispatch was derived from tensor dimensions, the stock tile and expert metadata. Under this model's configuration, the adaptive regime covered token counts from 116 through 512. It was not a branch on the benchmark's user labels.6

6.Dispatch by the problem Tensor shapes and expert occupancy are properties of the computation. “Four users” or “sixteen users” are labels from the evaluator. The optimization must work from the former.

In simplified pseudocode, the partition looks like this:

# Explanation only: real classification runs on the GPU.
local_ids = map_global_to_local(global_ids)  # -1 means non-local
live = local_ids >= 0
bins = where(live, local_ids, num_local_experts)
loads = histogram(bins, num_bins=num_local_experts + 1)
small = live & (loads[bins] <= 16)

small_ids = where(small, local_ids, -1)
large_ids = where((local_ids >= 0) & ~small, local_ids, -1)

# Each live route belongs to exactly one class.
run_marlin_for_class(small_ids, row_tile=32)
run_marlin_for_class(large_ids, row_tile=stock_tile)

The extra histogram bin keeps inactive routes from indexing with -1. They remain masked out regardless of that bin's count. The two execution classes must be disjoint, cover all live routes, and retain the original route weights and finalization semantics.

For the six-route excerpt in the figure, a rank maps [32, 33, 7, 32, 65, 33] to [0, 1, -1, 0, -1, 1]. Suppose the full forward assigns 12 routes to local expert 0 and 50 to local expert 1. The small output keeps [0, -1, -1, 0, -1, -1]; the large output keeps [-1, 1, -1, -1, -1, 1]. Nothing is dropped or counted twice among the live routes.7

7.Count the whole forward The six IDs are only an excerpt. The 12 and 50 come from the full histogram, not from counting the six drawn cells. Route weights stay attached to their original positions.

The implementation runs the two classes through the first projection, applies the existing activation, then runs the classes through the second projection. It retains Marlin's packed weights, scales and arithmetic operations. The two classes can share temporary storage only if one cannot overwrite the other’s live outputs. That also has to remain true under CUDA graph replay: a captured sequence of GPU operations is reused with new inputs at stable addresses. A test that repeatedly replays one input can miss stale-state bugs, so the replay tests changed the routes and checked the new outputs.

Fuse the integer work around the experts

The adaptive schedule introduced its own overhead: map IDs, count routes, classify experts and construct two masked route arrays. The next step was to combine that bookkeeping into one Triton kernel. Separate tensor operations cost launches and temporary tensors even when the work is integer indexing rather than matrix multiplication.

The GEMM People report was useful prior art for fusing small routing and dispatch operations. Its model and B200 hardware differed from this project, so the transferable idea was to reduce the bookkeeping—not to expect its measured speedup. 7

The fused classifier loads global IDs, maps them to local IDs, constructs a histogram, looks up each route's expert load, and writes the small and large route arrays. This is integer bookkeeping. It does not change activation precision, route weights or the expert GEMM equations.

Here the reference was straightforward to test exactly: every live route must appear once, every non-local route must stay inactive, and the two arrays must agree with the reference partition even as graph inputs change. Unlike the earlier tile change, this fusion did not alter a floating-point reduction.

The adaptive parent scored 1.0247×. Adding the fused classifier produced 1.0251×, the highest completed score in my project. That 0.0004 difference was nominal; separate runs did not establish that the classifier caused an improvement of that size. The stronger result was that the combined patch passed the official all-load evaluation. 88

8.Names matter “Fused-stock” in the results means the fused adaptive expert patch with stock launch flags. It is not unmodified stock SGLang.

A second opportunity: work before attention

The expert path now had a passing all-load result. I turned to another place where several small operations surrounded an expensive kernel: input preparation for FlashAttention-3, or FA3. The same launch-saving idea looked attractive here, but the data was floating-point and the writes changed persistent cache state.

In attention, a query Q is compared with keys K to determine how to combine values V. The KV cache retains keys and values from earlier tokens, so later generation can reuse them. Before attention, root mean square (RMS) normalization scales each Q/K head vector, and rotary position embeddings (RoPE) rotate Q and K to encode position. FA3 consumes the prepared tensors. My change was to that preparation, using the existing normalization, positional encoding and attention methods. 9

On the eligible path, stock normalized Q and K, applied RoPE where needed, converted K and V for the FP8 cache, stored the cache entries, and converted Q to FP8 for FA3. Instead of replacing attention, I explored folding some of that preparation into the existing QK kernel. SGLang already contained related fusion machinery; the work here was adapting its eligible FA3 path and preserving the backend's contracts. 10

Variant A fused the FP8 KV conversion and store while retaining a BF16 query output. The ordinary query cast remained before FA3. Variant B also emitted the FP8 query, making the downstream same-dtype cast a no-op. Both were built on the earlier fused expert patch, using stock launch flags.

Triton’s fused-softmax tutorial gives a small, runnable example of this idea: keep intermediate work in one kernel instead of repeatedly materializing tensors. In this case, however, one of the outputs was the cache that future tokens would read.

Moving the store means taking responsibility for it

The fused path had to write to the same full-attention or sliding-window cache locations as stock. Slot zero remained reserved for graph padding. Untouched slots had to remain untouched. A backend wait that protects cache ownership still had to happen before the new writer ran.

The dispatch was deliberately narrow: eligible FA3 decode or target-verify calls, the expected unscaled FP8 cache layout, and compatible buffers. Prefill, mixed batches, incompatible cache settings and other backends retained the ordinary path. “Can this kernel compute the values?” was only half the question. The other half was “who writes the cache when this branch is not taken?”9

9.Exactly one writer An eligible fused call owns the cache write. An ineligible call must restore the ordinary backend write. Getting the arithmetic right is insufficient if the fallback writes twice—or never writes.

The store also had to finish before attention read it. Programmatic Dependent Launch, or PDL, permits a dependent kernel to start before its producer fully finishes. The consumer must still wait before reading dependent data. Removing the separate query cast therefore required auditing the actual launch chain into FA3, rather than assuming that an unchanged Python call order guaranteed the needed device ordering. The pinned source audit found the ordinary launch boundary needed by the proposed path. That supported the implementation, but local L40 tests could not exercise the H200 PDL handoff. 10

Preserve the rounding boundary

Stock materializes BF16 values before the FP8 conversion. Fusing those operations must not accidentally convert an earlier FP32 intermediate directly to FP8. The intermediate rounding can change the result:

FP8(BF16(x)) can differ from FP8(x)

The implementation retained that intermediate rounding and matched the installed PyTorch version’s saturation and NaN behavior. Inspecting the pinned conversion code also corrected an early research note’s incorrect overflow claim. 1110

The earlier survey had already recorded a related warning from the NKI team 7013 report: moving a BF16 materialization boundary can change the integrated result. Keeping that rounding step was necessary. It was still not enough. 7

10.Fusion is not permission to skip rounding A temporary tensor may disappear; its numerical effect may still be required.

The local conversion tests included production-path byte comparisons and probes using all 65,536 BF16 input encodings. Those checks addressed conversion behavior; they did not exhaust the possible inputs to the normalization that produced those values.11

11.Study connectionGPU-accelerated Weight Teleportation is a useful parallel reading on avoiding intermediate handoffs. It concerns RL weight synchronization, not this serving patch. I did not implement its compression or weight-sync pipeline.

The failure hiding at a tile boundary

The most instructive bug appeared after the initial local tests and source reviews looked encouraging. A reviewer noticed that adding V rows changed the row count used to select a Triton launch configuration.

For this rank, Q has 16 heads and K has two. Stock QK preparation therefore uses 18 × T rows, where T is the token count. Including the two V heads changes the fused workload to 20 × T rows. The extra rows are real work, but they do not belong to the QK normalization whose numerical behavior I wanted to preserve.

At T = 56, stock sees 1,008 rows while fusion sees 1,120. They fall on opposite sides of a 1,024-row configuration boundary. At T = 410, the counts are 7,380 and 8,200, straddling another boundary at 8,192 rows.12

12.Two meanings of “row” The earlier Marlin row tile groups routed token activations for an expert. Here, Triton’s BLOCK_M groups head vectors for Q/K preparation. Both are tiling decisions, but they belong to different kernels and count different work.

Different tile families. This identifies a configuration boundary, not a prediction that every input will fail.

Targeted tests found query-byte failures in both original candidates. Variant A failed seven eager cases and eleven graph cases; Variant B failed two eager cases, at T = 410 and T = 416. The failures were finite values, independently reproducible—not just a disagreement over NaN representation. A’s T = 56 boundary can occur with seven eight-token verification requests. The larger T = 410 and T = 416 cases tested the kernel beyond the ordinary 32-user, eight-token verify regime; I retained those failures rather than exempting those inputs.

To isolate the cause, the controlled probes held the saved failing inputs fixed and varied the launch tile. Forcing stock to use the fused tile reproduced differences; matching stock’s tile fixed the original minimized failures. Another probe disabled arithmetic contraction, which changes whether eligible multiply/add operations combine into one rounded instruction. That did not remove the across-tile discrepancy.

The generated compiler code showed why the launch could matter. In one tile family, each thread accumulated four square contributions before exchanging partial results with other threads; another accumulated eight. FP32 addition is not associative: regrouping the additions can change the rounded sum.

For one head vector, RMS normalization scales each component by 1 / sqrt(mean(x²) + epsilon). A small change to the sum of squares changes that scale. Most outputs still round to the same BF16 value, but a value near a rounding midpoint can move to its neighbor. The following FP8 conversion can then expose the difference in the final query byte. The boundary fixtures found precisely the kind of case that broad random tests can miss.

The mathematical normalization formula had stayed the same; the finite-precision path implementing it had changed. NVIDIA’s floating-point guide explains the general reduction-order issue. The retained fixtures and controlled probes supplied the project-specific diagnosis. 12 13

The first repair was still incomplete

The first change selected the tile using stock's Q+K row count while keeping the grid large enough for Q+K+V:

# Simplified from the repaired FA3 preparation path.
config_rows = tokens * (num_q_heads + num_kv_heads)
block_m, num_warps = triton_config(config_rows)

work_rows = tokens * (num_q_heads + 2 * num_kv_heads)
grid = ceil_div(work_rows, block_m)

That fixed the original fixtures. A wider boundary sweep then found query/key discrepancies in the stock BLOCK_M = 32 family, including T = 3641. Matching the tile alone had failed again.

The final policy was therefore two-part: use stock’s Q+K row count to select the tile for supported families, and use the entire ordinary preparation path for the unsupported family. The fused grid still covered all Q+K+V rows when fusion was eligible. The wider-family arithmetic discrepancy remained unexplained; the fallback avoided executing it.13

13.A family, not a list of exceptions With these head counts, T = 3641 gives 18 × 3641 = 65,538 Q/K rows, entering the stock BLOCK_M = 32 family. Eligibility follows shape and head metadata rather than naming individual failing token counts.

From a repaired kernel to the final submission

Fixing the three minimized fixtures was the start of validation, not the end. The repaired candidate then passed a dense sweep in ordinary, uncaptured execution over every T from 1 through 512, both RoPE modes, and two finite seed families: 2,048 comparisons. Query bytes, BF16 key bytes, full cache bytes, dtypes and production stride were checked against an independently imported pinned-stock reference. Preserved failing fixtures failed before the repair and passed afterward.

Separate tests covered exceptional values, tile boundaries, changing graph inputs and cache locations, padded rows, untouched slots, and actual model dispatch back to stock. The model tests exercised real preparation and cache writes, but used a stand-in for the attention computation. Six configurations also compiled for SM90, the H200’s GPU architecture target. Compilation still did not execute FA3 or PDL on that hardware.14

14.2,048 means cases, not a proof 512 token counts × two RoPE modes × two finite seed families. It covers every count in that interval for those inputs, not every possible tensor value.

The local preparation measurements were encouraging: 4.56–5.21 μs per layer saved at the tested smaller sizes on the L40. These measurements included the device-side QK/RoPE preparation, casts and cache store. They excluded CPU dispatch, projections, FA3 itself, communication and the rest of serving. Those timings justified investigating fusion, but did not predict its H200 serving score.

This is where the queue became part of the engineering decision. At final selection, the repair’s H200 check was still queued. I chose the locally validated, independently reviewed repair for the last scored experiment, preserved the earlier 1.0251× entry, and recorded the missing integrated validation as a risk. The original A and B patches stayed blocked by their known failures. The final patch was repaired B on top of the fused expert schedule, with stock launch flags. Mixed chunking and the other experiments were left out. 14

When the scored run returned, it passed: all 176 reference turns, later-turn checks across 45,154 served positions, and memory 0.2 GB per GPU below stock. The exact submitted bundle had now run successfully in the official H200 server. The official pass refers to the evaluator’s model-agreement gates; it does not assert byte-identical full-model outputs. That was the missing integration evidence. The next question was whether it had improved the score.

What the serving results actually say

The score was 1.0224×, below the earlier fused expert schedule’s 1.0251×. The metric compares throughput at stock’s per-user interactivity point for each load and aggregates those ratios geometrically. In other words, it rewards throughput while accounting for the per-user serving rate, rather than reporting a kernel’s maximum raw tokens per second. The chart and table use those official frontier ratios. 1

Concurrent users Fused expert scheduling + Repaired attention preparation
1 1.0387× 1.0318×
4 1.0091× 1.0097×
16 1.0217× 1.0217×
32 1.0311× 1.0265×
Reported aggregate 1.0251× 1.0224×

The final run’s ratio was slightly higher at four users, matched at sixteen to the reported precision, and was lower at one and thirty-two. The aggregate difference is 0.0027, or about 0.263% relative to the earlier score. These were separate official runs with their own stock references, not randomized repeated comparisons between the two candidates.15

15.Read the denominator Each ratio compares a candidate with its stock reference. Comparing the two ratios does not turn the runs into a paired, repeated candidate-versus-candidate experiment.

The raw 32-user measurement reported one repetition. Its zero reported spread is not evidence of zero variability. Some latency measurements were also worse. These observations are reasons to investigate, not enough to assign the difference to fusion.

Why did local savings not become a higher score? The available evidence does not settle that. Hardware differences, integration overhead, branch frequency, the fraction of runtime affected and run variability are candidate explanations—not findings. The returned logs were truncated and contained no per-kernel activation counts or profiler trace. A useful next experiment would measure the actual branch coverage and exposed preparation time on the same H200 system before attributing the result to any one mechanism.

The full sequence of scored experiments makes the outcome easier to place. Mixed chunking remained a separate flag experiment; it was not part of the final repaired patch.

The branches I did not promote

The route from mapping to attention fusion was only the main thread. Alongside it, I investigated prefill GEMMs, tokenization, drafting and other scheduling changes. These branches explain why the final patch stayed relatively narrow.

Direction Why it was considered What stopped promotion
Expand NVFP4 weights, then use BF16 GEMM for large prefill A different compute regime might suit large chunks Numerical failures and poor complete-path local performance; no demonstrated serving benefit
Prefix-specialized Marlin scheduling Avoid generic expert-parallel overhead An unexplained watchdog stall; a later combined pass did not establish a repair
Cache tokenization of conversation segments Repeated long-prefix encoding looked avoidable Serialization overhead, tokenizer-mutation behavior and uncertain benchmark applicability
Shorter DFlash block Reduce work per verification step The 16-user check passed but returned an indicative 0.981 ratio
Mixed chunking Change how prefill and decode share execution Parent-plus-mixed scored 1.0241; fused-plus-mixed checks passed, but that exact combination did not receive an all-load score
Mask padding Stop padded rows from routing to experts Limited modeled headroom; not implemented in the final patch
Make route COUNT a runtime argument Avoid compiling a new classifier variant for each uncaptured count Unknown frequency and cost in serving; not implemented in the final patch
Replace the attention implementation Potentially reduce attention's larger streaming cost Substantial numerical, workspace, synchronization and target-hardware validation work remained

Some branches failed numerical tests; others passed but offered weak performance evidence, and some never reached a serving experiment. I kept those outcomes separate. In particular, the passing fused-plus-mixed checks could not be combined into an all-load score for a configuration I never submitted to that evaluation.

Public reports helped frame those decisions. alygg77's negative-results document and thethings.ai's projection worklog supplied counterexamples to assuming that less traffic, extra overlap or a better local proxy must improve the measured workload. The larger attention branch examined vjeux's public implementation and its derivatives; it was left unported. Those sources deserve credit even where the result was a decision not to adopt their technique. 1516

16.Negative results are useful results “This candidate failed” and “this entire idea can never work” are very different conclusions. The table records the former without claiming the latter.

What I would carry into the next project

I would get target-hardware feedback earlier. The L40 was valuable for rejecting incorrect code, but I spent the last part of the project qualifying a path whose H200 integration and benefit were still unknown. Earlier paired serving measurements would have made the final choice less speculative.

I would also design boundary tests alongside the first optimization, not after the first review. A dispatch heuristic is part of the executable program. Its thresholds deserve adjacent test cases, retained failure fixtures and changing-input replay just as much as the arithmetic body does.

The result I can claim is a best recorded 2.51% improvement on the challenge’s aggregate metric. The more involved attention patch passed but did not beat it. Its most useful lesson was concrete: adding V stores changed the launch geometry of a QK normalization, which changed rounding. Next time, I would test those dispatch boundaries from the first implementation—and get the whole-server measurement early enough to guide the next one.
